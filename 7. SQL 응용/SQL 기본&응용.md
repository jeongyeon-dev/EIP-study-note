*트랜잭션*  
추상적인 개념, DBMS 특성이라는데.. 일종의 "작업 기본 <u>단위</u>"라고 한다  
=> 실제 Spring 에서 작성한 경험으로는, 일종의 실행 묶음으로 보면 될 듯  

작업 단위인 만큼, 단위로서 기능해야 한다.  
이 묶음 요소들이 전부 다 수행되고 DB에 반영이 되면: COMMIT,  
중간에 삑사리가 나서 전부 다 묶음 요소 전으로 되돌리면: ROLLBACK,  
..그럼 CHECKPOINT는:  
묶음 단위에서 뒤로 가는 일종의 지점이라고 함. 예시로,  
```
@Transactional
public void order() {
    createOrder();
    decreaseStock();
    savePayment();
}
```
여기서 3개의 실행 단위가 하나의 트랜잭션이 되며, Check Point는 저 안의 지점에서 형성되지 않음  
아무튼 위 3개의 명령어를 TCL(Transcational Control Language)라고 함.  

당연히 그렇듯, 한 번에 되어야 하니 => **원자성**이 트랜잭션 특성 중 하나이다.  
또한 COMMIT 되면 DB에 영구 반영되기 때문에, **영속성**도 특성 중 하나,  
실행 단위로 인해 변경 수행되지 않는 요소들은 그대로 있어야 하므로 **일관성**,  
**고립성**.. 이라고 서로 트랜잭션 간 영향을 주지 말아야 한다는데, 뭘까?   
<br>

병행제어.. 는 <u>일관성</u>을 유지하기 위한 건데,  
같은 데이터를 동시에 읽고/수정할 때 서로의 중간 상태를 건드려서 DB가 꼬이는 걸 방지하는 것  
..으로 이해를 하면 될 듯 하다.  

기법도 몇 개 적혀있다. 외워야 할 듯 하는데, 표를 가져왔다:  
| 방식 | 충돌을 어떻게 해결? |
|---|---|
| 로킹 | 미리 막는다: 단순 무식? 편하게? |
| 낙관적 검증 | 일단 실행 후 마지막에 검사한다. 일단 하고 보자.. 식 |
| 타임스탬프 순서 | 시간 순서를 강제한다: 순서 부여 후 안 맞으면 rollback |
| MVCC | 버전단위? 잘 모름.. |


2PC(2 Phase Commit: 두 단계 커밋)  
두 단계로 나눴다. 분산 DB같은 경우, 서로 일치는 해야 하니까..

**DDL(Data Definition Language)** 알아보기  
스키마? 그 모호성에 대해..  데이터베이스의 구조, 제약조건 등의 정보를 담는 것..  
이라는데 꽤나 추상적인 개념.  

외부 스키마 - 개념 스키마 - 내부 스키마  
외부.. 말 그대로 보이는 것 그대로, 사용자에 따라 다르게 보이니.  
내부.. 이건 어떻게 저장이 될지. 하나의 형태? 예를 들어 B+ Tree 구조라던지, Hash Index라던지  
개념: 이 둘 사이의 징검다리 => 개발자가 보통 짜는 관점(제약조건, join 관계 등)  

거기에 독립성도 있다. 각각 계층?에서 표현하는 방식이 다른데, 서로 꼬이면 안되지 않나?  
-논리적 데이터 독립성: 개발자가 정의를 바꿔도 외부 뷰 관점에서는 변화 없을 수도 있으니  
-물리적 데이터 독립성: index라던지 이런 게 바뀌어도 개념 스키마가 변하진 않으니

*DDL 명령어 살펴보기*  
뭔가 장황하게 나열되어 있다.. 나름대로 예시를 들어 정리 해보면:  
CREATE TABLE 사원(사번 VARCHAR(10) NOT NULL, PRIMARY KEY(사번) .. 외래키, 제약);  
  
칼럼 추가 시 => ALTER TABLE 사원(ADD 전화번호 VARCHAR(11) UNIQUE);  
칼럼 변경 시 => ALTER TABLE 사원 ALTER 전화번호 NOT NULL;  
칼럼 삭제 시 => ALTER TABLE 사원 DROP DOWN 전화번호;  
  
DROP TABLE 사원; 이렇게 하면 아얘 삭제가 된다.  
옵션이 있다면..   
CASCADE: 참조하는 테이블까지 연쇄적으로 제거, RESTICT: 참조되고 있다면 삭제 안됨

=> 요렇게 하면 사번 관련해서 인텍스 걸리면, 사번으로 검색 시 알아서 빠르게 검색 됨  
.. 다만 조회할 때 조건이 맞아야 함, 인덱스 안걸린 칼럼으로 찾으면 완전순회 함

**DML(Data Manipulation Language)**  
말 그대로 조작어.. DB에 데이터를 삽입/수정/삭제/조회 할 때 쓰는 언어를 말한다.  
유명한 SELECT 절 부터: 
```
SELECT 이름, 과목  
FROM 성적  
WHERE 학점 = 'A'  
```
이런 방식인데, 여기에 WHERE 옵션을 추가하자면,  
WHERE 학점 IN ('A', 'B') => 둘 중 하나라도 되면 검색됨  
WHERE 학점 LIKE 'A%' => A로 시작되는.. 즉 'A+', A-' 등도 검색됨  
숫자차럼 >, < 가 되는 속성이라면 BETWEEN 10 AND 20(이상, 이하) 로 검색도 가능  
<br>

*응용을 해보자*  
```
SELECT 직책, COUNT(직책), SUM(급여),  
FROM 급여,
GROUP BY 직책;
```
여기서.. 위의 '직책'과 아래의 group by의 '직책' 둘이 있어서 select 문이 성립이 된다.  
위의 것이 없어면 group by로 무엇이 묶였는지 명시가 안될 뿐,  
각 직책 별로 그 수(count)와 합(sum)은 성립이 된다.  

무식?하게, 
```
SELECT COUNT(DISTINCT 직책), SUM(급여)  
FROM 급여;
```
하면 전체 합이 각각 칼럼으로 나오는데.. '직책' 칼럼에 distinct를 넣은 만큼,  
총 수가 아닌 개별 직책으로만 그 수가 표시된다.  

.. having 절은 무엇일까? => group by로 집계된 이후 조건을 적용하는 연산자?이다.  
예시를 작성한다면:  
```
SELECT 직책, COUNT(직책), SUM(급여) AS 급여합계,
FROM 급여
GROUP BY 직책
HAVING SUM(급여) >= 4000;
```
요런 식일 경우 이미 group by된 상황에서 sum이 된 것들 중 4천 미만인 row는 빠진다.

이제 **조인** 개념을 다시 훑어보자:  
교차 - 세타 - 동등 - 자연 - 외부 - 세미 - 셀프.. 이렇게 여러 가지 종류. 다 외워야 하나?  
대분류를 하면..  
교차(cross) 조인: 모든 행을 곱하기로 조인, 조건이 딱히 없다  
외부(outer) 조인: 불일치 행이 있는데, 이를 보존.. 그러니까 상대 테이블에 없으면 빈 칸으로 둠  
조건(inner) 조인:  
여기서 종류가 많이 펼쳐진다.. 먼저, *세타*의 경우 =, >, <, != 가 사용 가능하고, *동등*은 = 만  
가능, *자연*은 일치하는 행만 자동으로 조인?해준다고.. 

여기서 벗어나는 별도 관점으로 *세미(semi)*가 있으며 => 일치하는 행이 존재하는지만 확인  
*셀프*(같은 테이블끼리 조인)이 있다.  

마지막으로 **서브쿼리**가 있는데, 말 그대로 쿼리 내부에 쿼리 있는 것. 나도 앎.  
-FROM 절 서브 쿼리: from이니까 애초에 검색할 조건 대상 자체를 서브쿼리로 간추리는 것으로 이해  
-WHERE 절 서브 쿼리: 검색될 대상을 미리 쿼리로 만들어서 준다는 것으로 이해.. 예시로,  
```
SELECT MAX(가격) AS 가격
FROM 도서가격
WHERE 책번호 IN (SELECT 책번호 FROM 도서 WHERE 책명='주식%');
```
이런 식이라면 주식 관련된 책들의 모든 책번호를 기준으로 또 다시 검색을 한다는 점을 알 수 있음.

집합 연산자.. 말 그대로 집합 단위로 연산을 한다. 짧게 넘어가자  
UNION - 모든 집합.. 여기서 교집합을 중복하려면 UNION ALL을 하면 된다.  
교집합만 빼려면 INTERSECT 하면 되며, 특정 집합에서 교집합 부분만 빼려면 MINUS 하면 된다.  
  
마지막으로 DCL(Data Control Language)가 있다.  
권한 주고 뺐고 이런 건데.. GRANT UPDATE ON 학생 TO 정연; 이렇게 하면  
"정연"에게 "학생"테이블을 "UPDATE"하는 권한을 주는 것, 반대로  
REVOKE UPDATE ON 학생 FROM 정연; 하면 뺐는 것.
