데이터 모델링 => 순차(개념/논리/물리): 3회, 속성/관계: 2회, (구조/연산/제약조건): 2회, 키 관련: 2회  
DB 테이블 => 카디널리티/차수: 2회, 관계 대수(기호): 4회, 관계 해석?: 1회, 이상현상: 2회  
정규화 관련 => 개념: 4회, 종속관계: 1회

데이터를 모델링 할 때.. 가장 큰 틀을 이루는 3가지 축(표시해야 할 요소?)  
구조: 데이터를 어떤 형태로 표현하고 어떠한 관계 등을 형성하다록 해야 할까?  
연산: 그 데이터를 조회/변경 등을 하려면 어떠한 방식으로 해야 할까?  
제약조건: 어떠한 변경(조작) 등을 금지해야 할까?  

절차: 요구조건 분석 -> 개념적 설계 -> 논리적 설계 -> 물리적 설계  
개념적.. 은 현실을 모델로 옮기는 것, "개체-관계 다이어그램"이 예시라고..  
논리적.. 은 실제 데이터베이스 논리적 구조로 옮김: 테이블 설계, 정규화 하기 등  
물리적.. 은 실제 설계하는 거다. 코딩?으로. 보통 인덱싱 걸고, 반 정규화 등을 한다.  
<br>

테이블을 **릴레이션**이라고 하기도 한다. 보통 행렬로 이루어진 테이블.  
행 => 각 하나를 "튜플"이라 함 => 튜블의 수: 카디널리티  
열 => 각 하나를 "속성"이라 함 => 속성의 수: 차수(Degree)  
<br>

**관계 대수**: 릴레이션 대상으로 원하는 데이터를 구하는 "연산 체계"  

일반 집합 연산자: 수학에서 이미 "일반적"으로 사용 중인 것들..  
합집합(\(A \cup B\)): 둘을 합침. 중복되는 것은 하나로 처리  
교집합(\(A \cap B\)): 둘 안에 모두 속하는 튜플을 구함  
차집합(\(A - B\)): A에만 있고 B에는 없는 튜플들  
카디션 곱(\(A \times B\)): 무식하게? 튜플 간의 모든 조합을 구함  

순수 관계 연산자: 릴레이션을 처리하기 위해 "특화된" 연산자들..  
셀렉트(\(\sigma_{이름='철수'}(학생)\)): 속성 이름이 철수인 것을 뽑아라, 학생 릴레이션에서  
프로젝트(\(\pi_{\text{이름},{학년}}(\text{학생})\)): 학생 이름과 해당 학년만 추출  
조인(\(A\bowtie_{A.학번=B.학번}B\)): 우리가 알고있는 통상적인 그 "JOIN" 연산  
디비전(A÷B): A학생t, B과목t라 할때.. 학생 중 B의 과목들을 모두 수강한 학생들..  
<br>

개체-관계 모델.. E-R 모델  
릴리이션?인 "개체"가 있으며(ex. 학생, 교수)  
개체의 각 속성이 있다(ex. 학생 => 이름, 주소)  
개체 간의 관계도 있다(ex. 학생 ={지도}= 교수)  
<u>개념적 설계</u>에 속하므로.. 막 자세하게 구체적으로 다루진 않는 듯.  
<br>

**정규화**  
익숙하고, 헷깔리기도 한 그 이름.  
이상현상 <= 정규화가 이 문제를 해결하기 위해 존재.  
예를 들어, 정규화가 안된 한 테이블 예시를 보자:  
| 학번 | 학생 | 과목 | 교수 |  
|:---|:---|:---|:---|  
|1 | 철수 | 수학 | 김교수 |  
|1 | 철수 |	영어 | 이교수 |  
|2 | 영희 |	수학 | 김교수 |  

삽입 이상 => 아직 수강 안한 학생을 넣기 어려움  
갱신 이상 => 철수의 이름이 바뀌면 여러 행을 수정해야 함  
삭제 이상 => 영희 수강 정보를 삭제하면 영희 학생 정보까지 사라짐  

함수적 종속 관계?  
완전: 주민번호 -> 나 구별.. 이것이 완전 함수 종속, 이걸로 내 데이터를 모두? 식별이 가능하니까(빅브라더?)  
부분: (학번 + 과목) -> 점수, 이름 .. 여기서, "이름"은 저 키가 아닌 학번만에게만 부분적으로 종속됨  
이행: X -> Y -> Z 이런 관계.. 그럼 그냥 각각 쪼개버림 => X -> Y, Y -> Z  

정규화.. 데이터의 중복성을 제거해 "이상 현상"을 방지하고, 함수적 종속 관계를 이용한 "분해"과정  
-. 1차 정규화: 속성값을 원자값으로.. 한 속성에 여러 개가 없도록 한 단계  
-. 2차 정규화: 부분 함수적 종속 제거한 단계  
-. 3차 정규화: 이행 함수적 종속 제거한 단계  
=> 보통 여기까지만 시험에서 원리 물어봄.  

-. (보이스-코드) 정규화: 결정자이면서 후보키(ex. 교수)가 아닌 것 제거(ex. 학번 + 과목명 => 교수)  
-. 4차(다치 종속 제거) 정규화: .. 스킵 ..  
-. 5차(조인 종속성 이용) 정규화: 아무튼 조인이 되면 꼬이는 현상을 제거하기 위한 것  

**반 정규화**: 정규화 하면 조인이든 연산이 많아지니 이를 고려해서 반대로 하는 것.  
<br>  

무결성.. 정규화를 하면서 반드시 유지해야 하는 것, "데이터 무결성"이라고도 한다  
ex. 학생 테이블을 분리했다고 가정해보자(정규화 함)  
개체 무결성 => 학생 테이블을 식별해야 할 PK(학번)이 있어야 한다: NULL 안됨  
참조 무결성 => 수강 시, 수강 테이블에 식별 시 FK(학번)이 있어야 한다: 외래키.. 혹은 NULL 이어야 함  
속성 무결성 => 키가 아니지만, 지정된 규칙을 준수해야 한다: 학년에 -1 입력 허용 안하듯   

"키 무결성"은 키가 한 테이블에서 중복되면 안된다는 거고, "사용자 무결성"은 사용자가 직접 지정한  
규칙을 준수하는 것
